Spatial Search Export — Design Spec

Date: 2026-05-07 · Author: Elay (with Claude) · Status: design approved, awaiting implementation plan.

Goal

Convert the two MongoDB BSON dumps of the spatial-search task into a clean, analysis-ready CSV pair that mirrors the existing wikipedia data structure (Game.csv + KeyTable.csv), keyed by the wikipedia integer participant ID. The spatial-search records will then be join-compatible with data/cleaned_new/Game.csv via a single column.

Background & key findings

  • Two BSON files for the spatial_search_users_records collection live under data/Spatial Search Data/{1,2}/. They were split because of a backend issue. Each has a different MongoDB UUID; they do not overlap in their internal KeyTable.ID (dump1: 1..189, dump2: 190..243).
  • Combined: 495 records total, of which 273 are Version=Wikipedia_Exp_13.04; the rest are old test / version_1 sessions.
  • Linkage to wikipedia is not through the integer ID field. The two backends use independent ID counters and the same numeric ID can refer to different participants.
  • The reliable bridge is Prolific UserID. The wikipedia backend's KeyTable.csv (copied locally to data/Spatial Search Data/KeyTable.csv) maps wiki ID ↔ UserID (Prolific). The spatial-search records carry the same Prolific ID in their top-level UserId field.
  • Validation: 163/164 wiki Prolific UIDs match exactly one spatial-search record with Version=Wikipedia_Exp_13.04 and RunningName=Wikipedia_Exp_14.04. The 1 unmatched UID is elay96@gmail.com (test entries IDs 69, 70, already excluded by M52 IGNORED_PIDS). Zero duplicates, zero missing.
  • Final scope: 163 participants, 714,413 events.
  • Each participant is in exactly one experimental condition (Clumpy or Diffuse), not both. 87 participants are Clumpy, 76 are Diffuse. The condition assignment matches the wiki Condition column for every participant (100% agreement).

Pipeline

Single one-shot Python script: scripts/cleaning/spatial_search_export.py.

  1. Load wiki KeyTable. Filter to RunningName == 'Wikipedia_Exp_14.04' and Version != 'Updated Test'. Expected 163 rows after dropping elay96@gmail.com (IDs 69, 70).
  2. Load BSON. bson.decode_all on both files. Concatenate. Filter to Version == 'Wikipedia_Exp_13.04' AND RunningName == 'Wikipedia_Exp_14.04'. Expected 163 records.
  3. Build lookup {prolific_uid: spatial_record}. Hard-fail on duplicates (would indicate a data anomaly).
  4. Validate full match. For every wiki UID, assert there is exactly one matching spatial record. Hard-fail with the offending UIDs if not.
  5. Build Game.csv. For each wiki row, walk spatial_record.Records.Game[]. For each event:
    • Override the event's integer ID with the wiki ID.
    • Pick out the canonical 18 columns; missing fields become NaN/empty (preserve wiki Game.csv style).
    Concatenate per-participant frames and sort by (ID, Time).
  6. Build KeyTable.csv. Merge wiki KeyTable rows with the spatial-search metadata fields listed above.
  7. Write outputs with UTF-8 encoding, no index column.
  8. Final validation block (printed to stdout):
    • KeyTable row count == 163.
    • Every Game.csv ID is present in KeyTable.csv ID set.
    • Total Game.csv rows == sum of len(Records.Game) across the 163 selected spatial records.
    • Per-participant trial structure summary: number of Round_start events per (ID, GameCondition) — expected 1 for Training_Maze, 5 for Diffuse, 5 for Clumpy. Anomalies are reported but not hard-failed.

Non-goals

  • No re-derivation of switch rates, dwell times, or any analysis-level metrics. Those belong in the m-series scripts that consume Game.csv.
  • No JSON / Parquet outputs in this pass.
  • No exclusion of test users beyond the M52 IGNORED_PIDS = {69, 70} rule (which is already handled by the wiki KeyTable filter).
  • No backfill of records that exist in spatial-search but never produced a wiki session (test users, dropouts).
  • No conversion of Time strings to timezone-aware ISO timestamps. The downstream scripts work with the raw HH:MM:SS format.

Open questions / assumptions

  • Assumption: the existing wiki-side analysis pipeline keys on integer ID, so the spatial-search export inheriting that ID is the right primary key. (Confirmed by reviewing m1–m73.)
  • Assumption: the BSON-side Age / Gender in event payloads is identical to the wiki side. They sometimes differ (different self-reports across the two sessions) — we keep the spatial-search values as-is in Game.csv; the wiki Age/Gender are already in data/cleaned_new/Game.csv for cross-checking.
  • Each participant is assigned to one condition (Clumpy or Diffuse), so the validation block expects 5 Round_end events from a single condition column — not 5+5 across both. Participants with ≠ 5 Round_ends are reported as a soft warning, not a hard failure.

Acceptance criteria

  1. data/cleaned/spatial_search/Game.csv exists, 714,413 rows, 18 columns as specified.
  2. data/cleaned/spatial_search/KeyTable.csv exists, 163 rows, 12 columns as specified.
  3. The validation block at the end of the script prints all checks PASS.
  4. A pandas join on ID between the new Game.csv and data/cleaned_new/Game.csv succeeds for all 163 spatial IDs (every spatial ID is in the wiki Game.csv).
