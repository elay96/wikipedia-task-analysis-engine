Data Cleaning & Article Content Fetch - Design Spec

Date: 2026-04-20  ·  Author: Elay Guez (brainstormed with Claude)  ·  Status: Pending implementation

1. Context

The Wikipedia navigation experiment logged user trials into data/dirty_data/Game.csv. Two new columns were added to the schema, ArticleRevid and WikipediaUrl, but the server did not populate them for real participants. We need to backfill those columns by resolving the Wikipedia revision active at each article_open timestamp, then (as a separate deferred stage) download the corresponding article content for downstream LDA, PCA and embedding analyses.

Observed data state (after analysis of dirty CSV)

  • Shape: 4,867 rows × 31 columns; 38 users (incl. test users 69, 70)
  • 597 article_open events; only 13 already have ArticleRevid set - all belonging to test users 69/70 (to be removed)
  • 584 real-participant article_open rows need revid backfill (~193 unique slugs, ~250-300 unique (slug, timestamp) pairs once grouped by minute-bucket)
  • No missing timestamps, no missing slugs on article_open, no exact row duplicates
  • Date range: 2026-04-14 to 2026-04-20 (current; not future-dated artifacts)
  • 36 rows with NavigationType=NaN - all are the practice-landing Capybara open (expected, not a defect)
  • 220 answer_snapshot rows with identical text to a neighbor (debounce redundancy) - not treated as errors

2. Goals & Non-Goals

Goals

  1. Produce a cleaned CSV at data/cleaned/Game.csv where every non-practice article_open row has a correct ArticleRevid and WikipediaUrl.
  2. Remove test-user rows (IDs 69, 70).
  3. Normalise timestamps to a single ISO-8601 UTC format.
  4. Design (without implementing yet) a stage-2 script that downloads clean full-text article content per unique revid into data/cleaned/articles.jsonl.

Non-Goals

  • Modifying analysis scripts (m1_* through m52_*) to use the new file - that is a separate future step.
  • Deduping answer_snapshot rows (analysis code already handles this).
  • Normalising slug encoding (%20 vs _, case) - current slugs work unchanged.
  • Removing practice trials from the cleaned CSV.
  • Implementing stage 2 before stage 1 is verified by the user.

Design principles

  • Separation of concerns: slow network I/O is isolated from deterministic CSV transformation, so step1b can be re-run freely without re-hitting the API.
  • Idempotent & resumable: step1a reads its own output on startup and skips already-resolved entries.
  • Auditable: revid_lookup.csv is inspectable in a spreadsheet - easy to eyeball which slugs resolved cleanly vs. errored.
  • Manual gate before stage 2: no automated chain from stage 1 to stage 2; the user verifies the cleaned CSV first.

4. step1a_resolve_revids.py

Behaviour

For every unique (slug, timestamp) pair among article_open rows (after excluding users 69, 70), query the MediaWiki API for the revision that was current at that timestamp, following redirects automatically.

API call

GET https://en.wikipedia.org/w/api.php
  ?action=query
  &prop=revisions
  &titles={slug}
  &rvstart={timestamp}     # "give me the revision that was current no later than X"
  &rvdir=older
  &rvlimit=1
  &rvprop=ids|timestamp
  &redirects=1             # follow redirects automatically (user choice)
  &format=json

HTTP headers: User-Agent: WikipediaTaskAnalysis/1.0 (elay96@gmail.com) - required by MediaWiki's etiquette policy.

Output: data/cleaned/revid_lookup.csv

ColumnTypeExampleNotes
slugstrAquatic_plantsOriginal from CSV (unchanged)
timestampstr (ISO UTC)2026-04-14T13:18:30.751ZMatches the source row's Time
revidint or empty1349431902Empty on failure
statusstrok / not_found / errorAudit value
fetched_atstr2026-04-20T12:00:00ZDebug / cache invalidation

Rate limiting, retries, logging

  • Throttle: 50 ms between calls (~20 req/s), well below MediaWiki's informal limit
  • Retry policy: 3 attempts with exponential backoff (1s, 2s, 4s) on HTTP 429 / 5xx
  • Timeout: 30 s per request
  • Progress log: [n/total] resolved {slug}@{timestamp} → revid={id} every 50 calls
  • Final summary: total / ok / not_found / error counts + list of failed slugs

Resume behaviour

  • On startup, load existing revid_lookup.csv if present
  • Skip rows with status=ok; retry rows with status=error or missing entries

5. step1b_apply_cleaning.py

Inputs

  • data/dirty_data/Game.csv
  • data/cleaned/revid_lookup.csv (from step 1a)

Operations (ordered)

  1. Filter test users: drop all rows where ID ∈ {69, 70} (~122 rows removed)
  2. Timestamp normalisation: parse Time with pd.to_datetime(..., utc=True), re-serialise as YYYY-MM-DDTHH:MM:SS.fffZ (millisecond precision)
  3. Join revids: left-merge revid_lookup onto rows where Action=='article_open', keyed by ArticleSlug == lookup.slug AND Time == lookup.timestamp. Write the resolved revid into the existing ArticleRevid column. Other rows remain unchanged (this column is only meaningful for article_open).
  4. Build WikipediaUrl: for populated revid rows, set https://en.wikipedia.org/wiki/{ArticleSlug}?oldid={ArticleRevid}. Uses the original slug (MediaWiki resolves the revision regardless of page title in the URL).
  5. Validation gate (fail loudly if violated):
    • ≥95% of non-practice article_open rows must have non-null ArticleRevid
    • Every populated WikipediaUrl matches ^https://en\.wikipedia\.org/wiki/.+\?oldid=\d+$
    • No row has ID ∈ {69, 70}
    • Row count == (dirty row count) − 122
  6. Write output: data/cleaned/Game.csv, identical column order and set to the source

6. step2_fetch_articles.py (deferred - design only)

Not built until stage 1 output has been verified by the user. The design below is a contract, not a deliverable in this pass.

Inputs & outputs

  • Input: data/cleaned/Game.csv (post-verification)
  • Output: data/cleaned/articles.jsonl, one JSON object per line: 
    {"article_slug": "Capybara", "revid": 1349431902,
 "timestamp": "2026-04-14T13:15:03.415Z",
 "content": "The capybara (Hydrochoerus hydrochaeris) is ..."}

API call

GET https://en.wikipedia.org/w/api.php
  ?action=query
  &prop=extracts
  &explaintext=1           # plain text, no HTML
  &exsectionformat=plain
  &revids={revid}
  &redirects=1
  &format=json

Using extracts returns the full article body in clean plain text - no infoboxes, references, or navigation markup. Ideal for LDA / embeddings / PCA downstream.

Dedup & resume

  • Iterate over unique revids, not raw rows (~250-300 calls)
  • For each unique revid, set the record's timestamp to the earliest Time among all users/trials that visited that revid
  • On startup, read existing articles.jsonl and skip any revid already present

Reliability

Same rate-limit / retry / logging pattern as step1a (reuse the shared HTTP helper).

Validation

After completion: assert that every unique revid in the cleaned CSV has a corresponding line in articles.jsonl with non-empty content.

7. Testing Strategy

Unit tests

  • build_wikipedia_url(slug, revid) → str - asserts exact format
  • normalise_timestamp(raw) → str - handles varied input, outputs canonical form
  • Validation-gate function - unit tested against synthetic pass/fail DataFrames

Integration (live API, tiny)

  • step1a dry-run against 3 known slugs including a known redirect (Aquatic_plants → Aquatic_plant) and a known-good page (Capybara). Asserts status=ok and a plausible revid.

Manual checkpoint

  • After stage 1: eyeball revid_lookup.csv for not_found/error rows; spot-check 5 random rows in cleaned/Game.csv by opening the URL in a browser and confirming the page shown matches what the user would plausibly have seen.

8. Performance & Scale Notes

  • Stage 1 expected duration: ~250 API calls × 50 ms throttle + network ≈ 30-90 seconds. Well within a single interactive run.
  • Stage 2 expected duration: ~250 API calls, larger payloads (5-50 KB each) ≈ 1-3 minutes.
  • No need for parallelism or async - sequential HTTP with throttle is simpler and easier to reason about.
  • If the dataset grows 10×+ in future, the requests.Session can be swapped for httpx.AsyncClient with a semaphore without changing the output contract.

9. Open Assumptions

  • All article opens happen at the recorded Time; the API's "revision ≤ timestamp" query is a correct proxy for "what the user saw".
  • Redirect following is acceptable (user confirmed option 1 - no audit columns needed).
  • Full-text extracts are the right content format (user confirmed option 1 + A - clean text, full article).
  • The cleaned CSV becomes the new canonical input; helpers.py's DEFAULT_DATA pointer will be updated in a separate, later task.
